CURRENT IDENTIFIER DESIGN
The public/business-facing identifiers are:

CUS-YYYYMMDD-NNNNNN

Person:
PE-YYYYMMDD-NNNNNN

Legal Entity:
LE-YYYYMMDD-NNNNNN

Investigation:
INV-YYYYMMDD-NNNNNN

Internal UUIDs are still used internally as database primary keys and foreign keys.

IMPORTANT API RULE
Customer-facing APIs should expose CUS-... rather than internal Customer UUIDs.
Person-facing APIs should use PE-... rather than internal Person UUIDs.
LegalEntity-facing APIs should use LE-... rather than internal LegalEntity UUIDs.
Investigation-facing APIs should use INV-....

Internal UUIDs may remain inside the database and internal service logic where required.

CURRENT ARCHITECTURE
Customer:
- A Customer can be Individual or Company.
- Individual Customer is linked internally to a Person.
- Company Customer is linked internally to a LegalEntity.
- Individual Customers cannot access the company relationship endpoint.

Standalone entities:
- Person can be created independently through POST /persons.
- LegalEntity can be created independently through POST /legal-entities.
- A related Person or LegalEntity does NOT need to be a Customer.
- This is important: do not create Customers merely to represent related parties.

ENTITY RELATIONSHIPS
Company relationship endpoint:

POST /customers/{customer_number}/relationships

The source can be:
- Person via from_person_number = PE-...
- LegalEntity via from_legal_entity_number = LE-...

The target is the Company's internally linked LegalEntity, resolved from the CUS-... customer number.

Internally relationships store UUID foreign keys:
- from_person_id
- from_legal_entity_id
- to_legal_entity_id

But API responses should use:
- from_person_number
- from_legal_entity_number
- to_customer_number

Current supported relationship types include:
- OWNS
- CONTROLS
- DIRECTOR_OF
- AUTHORIZED_PERSON_OF
- AUTHORIZED_SIGNATORY_OF
- SHAREHOLDER_OF
- UBO_OF

Duplicate identical relationships should be rejected.

GET:
GET /customers/{customer_number}/relationships

This returns the company's relationships using business-facing identifiers.

SCREENING
All screening is investigation-based.

The main screening endpoint is:

POST /investigations/{investigation_number}/screening

Screening results are retrieved using:

GET /investigations/{investigation_number}/screening-results

There is also investigation review/decision functionality.

For a Company investigation, screening must include:
1. The company/legal entity itself
2. Relationship parties configured for the company

Relationship roles include:
- UBO
- Director
- Shareholder
- Controller
- Authorized Person
- Authorized Signatory

For an Individual Customer:
- Screen the individual itself.

For a Company:
- Screen the company itself separately
- Screen each relevant relationship party separately

Screening results should preserve:
- subject_type

- relationship_role
- screening_type
- provider/source
- result
- match confidence
- source UID

- match strength
- evidence strength
- evidence
- adverse media fields where applicable

Current screening types:
- SANCTIONS

SPRINT 4 — MULTI-SOURCE SANCTIONS SCREENING
We are now starting Phase 3 Sprint 4.

The purpose of Sprint 4 is to move from the existing OFAC-only sanctions capability to a multi-source sanctions screening engine.

The final source set should be treated as:

CORE / INTERNATIONAL:
1. UN Security Council Consolidated List
   Official:
   https://main.un.org/securitycouncil/en/content/un-sc-consolidated-list

MAJOR JURISDICTION:
2. OFAC SDN List
   Official:
   https://ofac.treasury.gov/sanctions-list-service

3. OFAC Consolidated Non-SDN Lists
   Official:
   https://ofac.treasury.gov/sanctions-list-service

4. UK Sanctions List (UKSL)
   Official:
   https://www.gov.uk/government/publications/the-uk-sanctions-list

5. EU Consolidated Financial Sanctions List
   Official:
   https://finance.ec.europa.eu/eu-and-world/sanctions-restrictive-measures/overview-sanctions-and-related-resources_en

INDIA-SPECIFIC:
6. India Ministry of Home Affairs / UAPA designated lists
   Official:
   https://www.mha.gov.in/en/divisionofmha/counter-terrorism-and-counter-radicalization-division

Do NOT attempt to implement every country's national sanctions list at this stage.

Architecture should be extensible so additional country-specific sources can be plugged in later without redesigning the screening engine.

Do NOT treat FATF grey/black lists as sanctions lists. They represent jurisdictional AML/CFT risk and should remain conceptually separate from sanctions screening.

SOURCE-BY-SOURCE SCREENING REQUIREMENT
Every source must produce its own result.

Example:

Subject
├── UN → MATCH
├── OFAC_SDN → NO_MATCH
├── OFAC_NON_SDN → NO_MATCH
├── UK → MATCH
├── EU → NO_MATCH
└── INDIA_MHA → NO_MATCH

Do not overwrite results from one source with another source.

SCORING REQUIREMENT
The existing risk/recommendation engine should aggregate the source results.

User requirement:

If the final calculated score reaches 100:
→ RECOMMEND BLOCK

Sentinel recommends the decision; it should not automatically modify customer status just because the score is 100.

Do not assume that every weak match immediately equals score 100.
The existing matching/evidence/scoring logic should determine the final score.
